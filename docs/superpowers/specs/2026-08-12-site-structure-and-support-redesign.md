# 网站结构调整与技术支持页改版设计

日期：2026-08-12

## 目标

本轮调整重新定义产品、技术支持及首页的页面职责：取消产品类别和产品详情 URL 中的 `products` 路径段；将当前 `/products/` 的内容复制到首页作为后续首页建设的产品展示基础；保留 `/products/` 作为临时占位页面；用新的“全创服务”设计替换原技术支持内容。

本规范是后续站点结构、实现计划、页面代码、站内链接、SEO 和测试的唯一依据。旧文档中与本规范冲突的产品路径或技术支持规划均以本规范为准，并应在实施阶段同步更新，避免保留两套说法。

## 最终路由结构

```text
首页  /

临时产品中心占位页  /products/

产品类别  /{category-slug}/
└── 产品详情  /{category-slug}/{product-slug}/

解决方案  /solutions/
└── 解决方案详情  /solutions/{solution-slug}/

技术支持  /support/

关于我们  /about/

页脚辅助页面
├── 隐私政策  /privacy/
└── 法律声明  /legal/
```

四个产品类别的正式路径为：

- `/two-way-radio/`
- `/shortwave-radio/`
- `/mesh-network/`
- `/ict-integration/`

产品详情示例为 `/two-way-radio/ly198/`。不得再生成或链接到 `/products/{category-slug}/` 和 `/products/{category-slug}/{product-slug}/`。

`/products/` 是明确保留的临时占位页，不属于已取消的产品嵌套路由。它当前可以继续显示现有产品中心内容，但顶部导航不再将其作为产品中心入口。

## 顶部导航

顶部导航仍包含首页、产品中心、解决方案、技术支持和关于我们五项。

- 首页指向 `/`。
- 产品中心直接指向 `/two-way-radio/`。
- 解决方案指向 `/solutions/`。
- 技术支持指向 `/support/`。
- 关于我们指向 `/about/`。

产品类别页及产品详情页均应将“产品中心”显示为当前导航项。当前状态判断不能再依赖 `/products/` 前缀，而应识别四个已发布产品类别的顶层路径。

## 首页与临时 `/products/` 页

### 当前阶段

首页应显示当前 `/products/` 页面已经完成的产品展示内容。`/products/` 页面和文件继续保留，并在当前阶段显示相同的可见内容。

### 迁移和复用边界

首页与 `/products/` 必须是两个独立页面，不共享完整页面模板，也不允许首页直接导入 `/products/` 页面文件。

允许复用稳定、职责单一的底层单元：

- `ProductCard` 产品卡片；
- 类别展示区块组件；
- 产品和类别数据查询 helper；
- 为两页准备当前展示数据的轻量 helper（如确有必要）。

两页应分别组合这些单元。当前视觉和内容相同不代表两页需要长期同步。

### 未来规则

未来 `/products/` 将改造成与首页完全不同的产品中心页面。届时可以直接替换 `/products/` 的页面结构，而不修改首页。产品卡片可继续复用，但其他区块是否复用应按届时需求决定。

未来给首页增加其他内容时，默认只修改首页，不自动同步到 `/products/`。未来重做 `/products/` 时，默认只修改 `/products/`，不自动同步到首页。任何跨页面同步必须由新需求明确提出。

## 产品类别与产品详情

### 类别页

四个类别使用同一个动态或参数化页面模板，避免生成四套独立布局。模板根据 `category-slug` 读取类别和产品数据。

类别页顶部必须包含：

- 当前类别名称和当前状态；
- 另外三个类别的入口；
- 在移动端仍可清楚识别和操作的类别切换布局。

四个入口应来自同一产品类别数据源，并按照统一 `sortOrder` 排列。页面不得硬编码两套类别名称或路径映射。

### 产品详情页

产品详情使用统一模板，通过 `category-slug` 和 `product-slug` 定位产品。页面必须验证产品确实属于 URL 中的类别；不匹配的组合不得生成静态页面。

所有产品卡片、类别页、面包屑、页脚和站内链接均使用新的无 `/products` 前缀路径。

## 技术支持 `/support/`

### 内容替换范围

原规划中的使用说明、FAQ 和售后服务全部取消。以下内容不得继续作为 `/support/` 的板块、子页面或页脚入口：

- 使用说明及产品资料分类页；
- 具体说明文档网页；
- FAQ 预览及 `/support/faq/`；
- 售后服务旧板块。

对应的示例 FAQ、说明文档内容集合和校验逻辑如已无其他用途，应在实施时删除。不得留下死链接、孤立测试或仍描述旧支持架构的文档。

### 新页面结构

新技术支持页参考用户提供的设计图，采用以下结构：

1. 居中的“全创服务”标题及英文副标题；
2. 六个浅灰色服务卡片；
3. “服务准则”标题、分隔线、说明文字和四项准则。

六项服务名称固定为：

1. 网络规划服务
2. 系统工程建设服务
3. 维护保障服务
4. 设备巡检服务
5. 通讯保障服务
6. 技术培训服务

卡片包含匹配主题的蓝色线性图标、中文标题和简短说明。使用与参考图接近且授权清晰的现有图标库；不得使用 emoji、文本符号、CSS 图形或手绘内联 SVG 代替图标。

### 响应式布局

- 桌面端：三列两行（3 × 2）。
- 移动端：两列三行（2 × 3）。
- 不允许在常规移动端直接退化为单列。
- 卡片文本应通过字号、间距和自动换行适配窄屏，不采用横向滚动。
- 所有卡片在同一行保持一致高度，并保持清晰的触控间距。

### 卡片交互和未来链接

本轮卡片是静态展示，不创建六个服务详情页，也不输出不可用的假链接。

服务数据结构应预留可选的 `href` 字段。仅当某项具有真实目标地址时才渲染为链接；没有 `href` 时渲染为非交互内容，不能使用 `#`、空地址或统一指向 `/support/` 冒充详情页。

未来添加服务详情页时，只需补充真实 `href` 并由同一数据源同时驱动卡片和页脚链接，不重新编写卡片布局。

### 服务准则

页面保留参考图中的说明层级：标题、蓝色短下划线、横向分隔线、简介和四项准则。四项准则为响应时效、专业水准、安全可靠和全程无忧；具体公开文案可在正式资料到位后替换，占位文案不得被描述为已确认的公司承诺。

## 页脚

页脚“技术支持”栏目应包含七个可见主题：

- 技术支持（链接 `/support/`）；
- 网络规划服务；
- 系统工程建设服务；
- 维护保障服务；
- 设备巡检服务；
- 通讯保障服务；
- 技术培训服务。

本轮只有“技术支持”拥有真实链接。六个服务主题需要显示，但在没有详情页时使用非链接文本，不得统一链接回 `/support/`，以免误导用户。

未来某服务有真实目标地址后，页脚与卡片必须从同一服务数据源读取并同时启用对应链接。旧的“使用说明”“常见问题”“售后服务”页脚项全部删除。

页脚产品栏目中的类别入口使用新的顶层类别路径。“全部产品”如继续保留，应明确指向临时 `/products/` 占位页，并在未来产品中心重做时重新评估；不得将它与顶部“产品中心”的 `/two-way-radio/` 入口混为同一规则。

## 保持不变的页面

- `/solutions/` 和 `/solutions/{solution-slug}/` 的路由及页面职责保持不变。
- `/about/` 的路由及页面职责保持不变。
- 隐私政策和法律声明的既有规划保持不变。

保持不变不代表可以保留指向旧产品或旧支持路径的站内链接；所有受路由调整影响的链接仍必须同步更新。

## 内容模型与清理

产品类别和产品内容模型继续保留。产品路径由类别与产品 slug 组合生成，不在内容中重复保存带 `/products` 的固定 URL。

新建一个集中维护的服务主题数据源，至少包含：

- 稳定的服务 `id`；
- 中文名称；
- 简短说明；
- 图标标识；
- 可选 `href`。

该数据源同时供 support 卡片和页脚使用，防止名称、顺序和链接不一致。

旧 `documents` 和 `faq` 内容集合若确认仅用于已取消的技术支持内容，应删除其 schema、内容文件、业务校验和测试。不要为了“可能以后使用”继续保留会暗示现行信息架构仍支持这些页面的死模型；未来如重新提出文档或 FAQ 需求，再按新需求建立。

## SEO、站点地图和导航辅助

实施必须同步更新：

- canonical URL；
- sitemap 生成结果；
- 面包屑；
- 顶部导航当前状态；
- 页脚链接；
- 产品卡片链接；
- 类别切换链接；
- 测试夹具及路径断言；
- `SiteMap.md`、项目状态和仍被维护的规划文档中的现行结论。

不得生成旧产品嵌套路由。由于旧站尚未上线，本轮不主动建立旧 `/products/{category-slug}/...` 重定向；如果以后提供正式旧 URL 清单，再在上线迁移阶段单独设计重定向表。

`/` 与 `/products/` 内容相同但 canonical 必须分别反映各自页面职责：主页 canonical 为 `/`，临时产品页 canonical 为 `/products/`。不得把 `/products/` canonical 指向首页，除非未来另行决定将其视为重复页面或取消索引。

## 验证要求

实施完成后至少验证：

- `/` 与 `/products/` 当前均显示完整产品展示内容；
- 两个页面为独立页面组合，没有整页互相导入；
- 顶部“产品中心”进入 `/two-way-radio/`；
- 四个类别路径均生成，并共享模板；
- 类别页能显示当前类别和另外三个入口；
- 产品详情只生成新的两级顶层路径；
- 旧 `/products/{category-slug}/...` 不生成；
- `/support/` 桌面端为 3 × 2，移动端为 2 × 3；
- 六项服务名称在 support 与页脚完全一致；
- 六项服务没有真实地址时不呈现为假链接；
- 旧 FAQ、使用说明和售后服务入口均消失；
- solutions 和 about 路径未被破坏；
- 内容校验、类型检查、静态构建、单元测试和端到端测试通过；
- 对 support 参考图与相同视口的实现截图完成视觉对比，并通过设计 QA。

## 明确不在本轮范围内

- 重做未来的正式 `/products/` 产品中心；
- 为六项服务创建详情页面；
- 为首页添加产品展示之外的新区块；
- 改造 solutions 或 about 页面内容；
- 部署网站或切换正式域名；
- 未经正式资料确认而编造公司服务承诺、联系方式或业务数据。
